# osu! skin 请求路由

本文件是入口路由。先匹配意图，再加载对应 reference。除非任务跨多个域，不要加载全部文件。

读取匹配的 reference，并运行其中直接列出的 `osu-skin <子命令>`；首次选择工具时先读取 `tools.md` 的工具总表和按需求选择表。命令不可用时先从 Skill 根目录运行 `python -m pip install -e .`；命令返回非零退出码时读取结构化错误，不把部分输出当成成功。

## 0. 请求预检

先从用户输入和工作区读取以下事实：

| 事实 | 获取方式 | 不确定时 |
|---|---|---|
| 输入类型 | 看路径扩展名、目录内容和用户描述 | 询问用户要处理目录、压缩包还是单个素材 |
| 皮肤根目录 | 找到包含 `skin.ini` 或明确 skin 文件集的目录 | 询问路径，不能把整个 workspace 当皮肤 |
| 客户端 | 用户明确说明；否则检查根目录 `skininfo.json` | 无该文件时必须询问 stable/lazer |
| 模式 | 用户描述、`skin.ini`、文件名和数据库标签 | 询问 std/taiko/catch/mania |
| Mania keycount | `[Mania]` 段的 `Keys` | 用户没有指定时询问具体键数 |
| 修改范围 | 请求中的资源组、模式、keycount、界面 | 询问保留/修改范围 |
| 覆盖策略 | 用户是否要求原地修改 | 默认新建输出目录 |

### 客户端闸门

按以下顺序执行，后面的规则不能绕过前面的确认：

1. 用户明确说 stable/lazer：记录为用户声明。
2. 皮肤根目录存在 `skininfo.json`：记录为文件证据，判定 lazer。
3. 没有 `skininfo.json` 且用户没有声明：停止客户端相关判断，向用户询问 stable 或 lazer。
4. 用户声明与文件证据冲突：停止写入并询问哪个作为目标。
5. `MainHUDComponents.json`、`SongSelect.json`、`Playfield.json`、目录名、扩展名和“看起来像 lazer”都不能替代确认。

### 视觉故障的文件闸门

用户问“为什么变形”“怎么修复”但没有提供实际皮肤时，第一轮先索要：

1. 可读取的皮肤目录、`.osk`/zip，或至少 `skin.ini` 与实际相关 PNG；
2. Mania 问题对应的 keycount。

用户的文字描述不能证明实际加载的 path、SD/`@2x`、动画帧、alpha 或 `NoteBodyStyle`。拿到文件前只说明后续检查步骤，不猜文件名、尺寸、字段值或直接给修复参数。用户已说明“stable 移到 lazer”时，客户端信息已经足够，不再追问客户端。

## 2. 只读与写入分界

### 可以直接开始的只读任务

- 查询元素或字段含义；
- 检查文件是否存在、尺寸、命名、alpha、帧序和音频格式；
- 对没有客户端依赖的素材做哈希、对比或统计；
- 在客户端未知时列出候选原因，但必须标记为未确认。

### 必须先确认的写入任务

- 任何依赖 stable/lazer 行为的修改；
- 删除、覆盖、原地批量处理或安装到 osu! 目录；
- Mania keycount 合并；
- 将一个资源组覆盖另一个资源组；
- 可能改变视觉位置的裁切、画布调整和舞台字段修改。

## 3. 通用执行模板

按以下阶段执行，阶段不能省略：

1. **定位**：确认根目录、输入文件和目标客户端。
2. **解释**：从数据库和 reference 找出元素、字段、回退和依赖。
3. **计划**：列出将读取、复制、修改、重命名、删除的对象。
4. **执行**：使用当前环境的文件、shell、SQLite、图像或音频能力。
5. **复检**：重新读取输出，检查路径、字段、资源存在性和客户端风险。
6. **交付**：给出变更清单、验证结果、警告、来源和回退位置。

## 4. 证据标签

每条诊断结论使用以下标签之一：

- `已确认`：由用户声明、文件存在性、数据库记录或工具指标直接证明。
- `客户端规则`：由 stable/lazer 规则或数据库 `client`/notes 说明。
- `高概率`：症状和证据吻合，但没有运行客户端验证。
- `待确认`：需要用户补充客户端选择、分辨率、谱面或更多文件。

不要把 `高概率` 写成确定事实。

## 5. 必须提问的最小问题

只问会改变处理路径的问题：

1. 目录没有 `skininfo.json` 时：按 stable 还是 lazer 处理？
2. Mania 请求没有键数时：处理哪个 keycount？
3. 没有“投/投皮”语境的普通“长度/大小/位置”有多种含义时：指谱面行为、图片尺寸还是舞台坐标？
4. 混皮没有范围时：保留哪些模式、界面和音效？
5. 任意单模式替换包含跨模式图片或全局配置时：列出其在其他模式的作用后，询问是否覆盖？
6. 有覆盖/删除风险时：生成新目录还是修改原目录？
7. Mania 中的“尾/面尾/后面尾/收尾”变形但没有皮肤证据时：请提供皮肤和 keycount；不能先把“尾”判成 `NoteImage#T`。
